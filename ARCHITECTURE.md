# SocialApp Architecture & Codebase Guide

This document provides a comprehensive overview of the **SocialApp** backend architecture, design patterns, core conventions, and essential insights ("skills") for rapid navigation and feature implementation.

---

## 1. High-Level Architecture & Domain Modules

The project follows a modular, domain-driven package organization under `com.example.socialapp`:

```
com.example.socialapp
├── account/             # User accounts, profiles, password/email/phone changes
├── auth/                # Authentication, JWT issuance, OTP verification (Email/SMS)
├── common/              # Shared utilities, responses, exceptions, file storage
│   ├── dto/             # Standard ApiResponse envelope
│   ├── exception/       # ApiException hierarchy, ErrorCode, GlobalExceptionHandler
│   ├── extentions/      # Kotlin extensions (e.g., .tr() for localization)
│   └── storage/         # FileStorageService (Local / S3), FileCategory, MediaController
├── config/              # Spring configuration (Security, I18n, Async, OpenAPI, RateLimit)
├── identity/            # Dual-identifier logic (Email or Phone auth switching)
├── post/                # Posts, media attachments, comments, and reactions
│   ├── comment/         # PostComment entity & logic
│   ├── dto/             # Request & Response DTOs (PostRequest, etc.)
│   ├── entites/         # Post, PostImage JPA entities
│   ├── reaction/        # PostLike entity, Reaction enum, native reaction queries
│   ├── PostRepository   # Optimized native SQL CTE queries & projections
│   └── PostService      # Post domain orchestration & file attachments
├── security/            # JWT authentication filter & token parsing
│   └── ratelimit/       # Annotation-driven rate limiter (@RateLimit)
└── sharelink/           # Deep link handling for mobile clients (Android/iOS)
```

## 2. Core Conventions & Design Patterns

### 2.1 Kotlin DTO Validation (`@field:` Target)
In Kotlin data classes, constructor parameters can represent constructor arguments, properties, and backing fields. Jakarta Bean Validation only scans bean fields or getters:
- **Rule**: Always prefix constraint annotations with `@field:`:
  ```kotlin
  data class ExampleRequest(
      @field:NotBlank(message = "{validation.cannot_be_blank}")
      @field:Size(min = 3, max = 255, message = "{validation.post.title.size}")
      val title: String,

      @field:Size(max = 10, message = "{validation.post.images.max}")
      val images: List<MultipartFile>? = null,
  )
  ```
- **Nullable optional fields**: Default them to `null` (`= null`) so callers or JSON deserializers do not fail when omitted.

### 2.2 Internationalization (i18n) & Validation Messages
- **Files**:
  - `src/main/resources/messages.properties` (Default / English fallback)
  - `src/main/resources/messages_ar.properties` (Arabic translations)
- **Configuration**: `I18nConfig` registers an `AcceptHeaderLocaleResolver` (supporting English and Arabic) and feeds `MessageSource` into `LocalValidatorFactoryBean`.
- **Message Reference**: Place keys in brackets `{validation.key_name}` in validation annotations. Spring automatically interpolates the localized message based on the incoming `Accept-Language` header.
- **Manual Translation in Code**: Use the `.tr()` extension function:
  ```kotlin
  throw ApiException.NotFound("error.post.not_found")
  ```
  The `GlobalExceptionHandler` converts `ApiException` error codes into localized strings using `.tr()`.

### 2.3 API Response Envelope & Global Error Handling
All responses follow a consistent `ApiResponse<T>` envelope:
- **Success**: `ApiResponse.ok(data)`
- **Failure**: Handled centrally by `GlobalExceptionHandler`:
  - `ApiException`: Translated business errors mapped to HTTP status codes.
  - `MethodArgumentNotValidException`: Formatted as `field: error message`.
  - `MaxUploadSizeExceededException`: Catches file size limit overages (`error.file.too_large`).
  - `OptimisticLockingFailureException`: 409 Conflict with `error.concurrent_modification`.

### 2.4 File Storage (`FileStorageService` & `FileCategory`)
- Uploads are segmented into strongly-typed `FileCategory` instances (e.g. `AVATAR`, `IMAGES`).
- Each category enforces:
  - Max file size (e.g. 5 MB).
  - Allowed MIME types verified via **magic-byte sniffing** (not trusting client file extensions).
  - Storage directory / key prefix.
  - Visibility (`PUBLIC` serviced through `/media/{category}/{filename}` with caching and compression, or `PRIVATE`).

### 2.5 Database Migrations & JPA
- **Flyway**: Located in `src/main/resources/db/migration/`.
- **Validation**: `spring.jpa.hibernate.ddl-auto: validate` ensures DB schema matches JPA entities strictly.
- **UUIDs**: All primary keys use UUIDs generated by DB (`gen_random_uuid()`) or JPA (`@GeneratedValue(strategy = GenerationType.UUID)`).

## 3. Fast Codebase Navigation & Comprehension Skills

When inspecting, extending, or debugging this codebase, apply these practical patterns:

| Skill / Goal | Where to Look | Fast Command / Shortcut |
| :--- | :--- | :--- |
| **Check Flyway DB Schema** | `src/main/resources/db/migration/` | Inspect `V1__init.sql` to verify column names, nullability, foreign keys, and indexes before writing entities/DTOs. |
| **Trace Request Flow** | `Controller` -> `Service` -> `Repository` | Check `controller/` for route & `@Valid`, `Service` for transactions/business logic, `Repository` for queries. |
| **Find Validation Messages** | `messages.properties` & `messages_ar.properties` | Search `validation.` or `error.` keys. Both files must stay in sync when adding new keys. |
| **Check Storage Capabilities** | `common/storage/FileCategory.kt` | Check accepted media types (`MEDIA_EXTENSIONS`), size caps, and URL path rules. |
| **Check Active Config Profiles** | `application.yaml`, `application-dev.yaml`, `application-prod.yaml` | Verify properties for datasource, redis, mail, storage, and JWT secrets. |
| **Inspect Custom Annotations** | `identity/ValidIdentifier.kt`, `security/ratelimit/annotation/RateLimit.kt` | Custom validator implementations and AOP aspects that intercept requests. |

## 4. How to Add a New Feature (Step-by-Step Checklist)

1. **Database Migration**:
   - Add table / column definitions in `V...__name.sql`.
   - Add appropriate indexes for foreign keys and lookup queries.
2. **JPA Entity**:
   - Create entity in `<module>/entites/`.
   - Configure relationships (`@ManyToOne`, `@OneToMany`), `@OnDelete`, `@JoinColumn`, and timestamps.
3. **Request & Response DTOs**:
   - Create request in `<module>/dto/`.
   - Apply `@field:NotBlank`, `@field:Size`, etc.
   - Apply `@Schema` and `@field:Schema` for Swagger documentation.
4. **Translations**:
   - Add error and validation messages to both `messages.properties` and `messages_ar.properties`.
5. **Repository & Service**:
   - Create Spring Data JPA repository or native queries/projections.
   - Implement business logic, permission checks, and transaction boundaries.
6. **Controller**:
   - Expose endpoints with `@PreAuthorize`, `@Valid`, `@RateLimit` where applicable.
